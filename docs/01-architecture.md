# Архитектура, фундамент и этапы разработки

Nov 21, 2026 · @Hara

## Архитектура

Вся логика обучения собрана в одном ядре на Rust. Сервер вызывает его нативно, PWA — через WASM, поэтому проверка ответов и модель ученика работают без интернета и считают одинаково.

&#91;embedded content: компоненты платформы · 9 частей\]

Контент попадает в базу только через проверки content-build. Аудио генерируется один раз и дальше отдаётся статикой. Сервер и PWA обмениваются событиями в обе стороны.

## Фундамент с первого дня

Критерий простой: закладываем сразу то, что потом придётся переделывать во всём коде или терять данные. Всё остальное добавляется по мере надобности.

| Что | Зачем | Цена, если отложить |
| --- | --- | --- |
| **Чистое ядро на Rust без ввода-вывода** | проверка ответов, модель ученика и планировщик — чистые функции; один код работает на сервере и в браузере через WASM | две реализации (Rust и TS), которые расходятся, и офлайн считает не так, как сервер |
| **Лог событий с версией схемы** | у каждого события `schema_version`; старые события читаются через преобразователи (upcasters) | потеря истории учеников при первом же изменении формата |
| **Тип задания как модуль** | трейт `ItemKind`: схема данных + проверка + компонент отрисовки; новый тип не трогает ядро | каждый новый тип задания правит полпроекта |
| **Модель ученика как интерфейс** | трейт `LearnerModel`; новую модель можно запустить «в тени» рядом со старой и сравнить точность прогнозов на реальном логе | алгоритм нельзя улучшать без риска сломать рекомендации |
| **Общие типы API** | TypeScript-типы генерируются из Rust (ts-rs или specta) | рассинхрон сервера и клиента, ошибки в рантайме |
| **Offline-first с самого начала** | клиент пишет события локально (UUIDv7), синхронизация идемпотентна, конфликтов нет: лог только дописывается | переписывание всего слоя данных клиента |
| **i18n с первой строки** | все строки интерфейса через ключи Fluent; он правильно склоняет числа в русском | ручной вылов сотен захардкоженных строк |
| **Роли и права** | learner, mentor, author, admin; ментор видит своих учеников | переделка авторизации во всех эндпоинтах |
| **Тесты пересчётом лога** | реальные логи проигрываются на новой версии ядра; свойства проверяются через proptest | тихие регрессии в модели, которые невозможно заметить глазами |
| **Наблюдаемость** | tracing + метрики Prometheus, плюс метрики качества модели (точность прогнозов) | система ошибается, и никто об этом не знает |
| **Бэкапы лога** | архивация WAL Postgres (pgBackRest); лог — единственные данные, которые нельзя восстановить | потеря месяцев данных учеников |
| **Воспроизводимая сборка** | монорепо + Nix flake: окружение, сборка, деплой на NixOS | «у меня работает» и ручной деплой |

**Производительность закладывается на этапе сборки контента, а не в рантайме.** Компилятор заранее считает транзитивное замыкание графа, компилирует шаблоны ответов в автоматы и строит индексы заданий по KC. Состояние модели ученика хранится снапшотом и обновляется инкрементально, аудио отдаётся статикой и кэшируется на устройстве.

**Намеренно откладываем:** микросервисы, очереди сообщений, многосерверность. Для десятков и даже тысяч учеников хватит одного сервера с монолитом; чистые границы модулей позволят разделить его потом, если понадобится.

## Стек

Основа — Rust на сервере и в ядре, TypeScript только в интерфейсе. Вся логика обучения живёт в Rust, клиент её только вызывает.

| Компонент | Выбор | Почему |
| --- | --- | --- |
| Ядро обучения | Rust, crate без ввода-вывода → нативно и WASM | одна реализация для сервера и офлайн-клиента |
| Сервер | axum + tokio, sqlx | тот же стек, что в fikr; sqlx проверяет SQL-запросы при компиляции |
| База данных | PostgreSQL | контент, лог событий, снапшоты модели; надёжные бэкапы через WAL |
| Клиент | TypeScript + SolidJS, Vite, PWA | маленький бандл, точечная реактивность, быстро на слабых телефонах |
| Хранилище на устройстве | IndexedDB | лог событий до синхронизации и кэш контента |
| Контент | Nickel → JSON → CLI `content-build` на Rust | типизация при написании, полная проверка при сборке |
| Интервальные повторения | fsrs-rs | официальная реализация FSRS на Rust |
| Проверка письма | Hunspell, LanguageTool (локальный сервер) | правила без ИИ, работают без интернета |
| Аудио | скрипты → Piper или Kokoro → Opus, отдаёт nginx | генерация один раз, дальше статика и кэш |
| Локализация | Fluent (fluent-rs, @fluent/bundle) | склонения и множественное число в uz/ru/en |
| Деплой | Nix flake + модуль NixOS, systemd | одна команда, откат на предыдущую версию |
| Наблюдаемость | tracing, Prometheus, Grafana | уже знакомо по работе с инфраструктурой |

**Haskell — по желанию, только для content-build.** Это компилятор контента: разбор языка шаблонов ответов, проверки, сборка автоматов. Он работает только при сборке, а Rust-ядро лишь исполняет готовые автоматы. Цена: типы контента описаны в двух языках, их синхронизирует общая JSON-схема. Ядро и сервер остаются на Rust.

## Этапы

Восемь этапов, у каждого измеримый критерий перехода. Сроки — грубая оценка для одного разработчика по вечерам и выходным: всего около 13–17 месяцев до IELTS-режима. Важнее другое: польза начинается после этапа 1, а не в конце.

| Этап | Что входит |
| --- | --- |
| 0. Фундамент | монорепо, Nix flake, CI; типы домена в ядре; content-build с проверками; схема БД и лог событий |

| 2. Placement и планировщик | адаптивный placement; планировщик сессий; карта знаний; «почему это задание»; режим ментора; грамматика до B1, около 120 KC |

| 7. Speaking | сравнение интонации через DSP; потом фонемная оценка произношения |

## Социальные функции и инструменты

Всё это строится на том же логе событий: достижение, серия дней и прогресс команды — ещё одна свёртка лога. Поэтому новое достижение можно выдать задним числом всем, кто его уже заслужил.

| Функция | Как сделать правильно | Этап |
| --- | --- | --- |
| Помодоро | встроен в сессию: блок 25 минут = одна сессия планировщика, перерыв без заданий | 1 |
| Telegram-бот | напоминание, когда накопились повторения; итог дня; уведомления ментору; вход через Telegram | 1 |
| Команды | создание, приглашение по ссылке или ID; общие цели; владелец команды может быть ментором | 2 |
| Друзья | заявка по ID или из команды | 2 |
| Публичный профиль | уровень, достижения, рамка, серия дней; карта ошибок и слабые места видны только самому ученику и ментору | 2 |
| Достижения | за результаты: освоена тема, 30 дней подряд, первый мок, 10 прочитанных книг | 3 |
| Рамки профиля | открываются достижениями | 3 |

Принципы:

- **Награда за результат, а не за клики.** Очки за время или количество заданий подталкивают решать лёгкое — именно так происходит в Duolingo.
- **Командные цели вместо общего рейтинга.** Соревнование мотивирует сильных и отталкивает слабых. Рейтинг, если нужен, считается по освоенным темам и регулярности и только внутри команды.
- **Серия дней с заморозкой.** Один пропущенный день не обнуляет серию, иначе она становится источником тревоги.
- **Безопасность детей.** У младших профиль по умолчанию закрыт, личных сообщений от незнакомых нет, общение только внутри команды.

В фундамент с этапа 0: уведомления — отдельный модуль с каналами (Telegram, push, почта); социальный граф и настройки приватности закладываются в схему БД сразу.

### Инструменты и чат

| Инструмент | Что делает | Этап |
| --- | --- | --- |
| Офлайн-пакеты | скачать уроки, тексты и аудио на неделю вперёд | 1 |
| Тетрадь ошибок | собирается сама из лога: ошибка, исправление, правило | 2 |
| Обратный отсчёт до экзамена | дата экзамена → план нагрузки по неделям с учётом слабых мест | 2 |
| Чат в реальном времени | чаты команд и личные между друзьями; в сообщение вкладывается задание, слово или заметка как живая карточка; «вызов» — отправить другу задание | 2–3 |
| Заметки с графом | markdown со ссылками `[[...]]` и обратными ссылками; заметка привязывается к KC, слову или тексту; граф заметок поверх карты знаний | 3 |
| Личный словарь | слова из библиотеки вместе с предложением, сразу в повторения | 3 |

**Чат технически.** WebSocket в axum; на одном сервере — рассылка внутри процесса, при росте — Postgres LISTEN/NOTIFY. История в Postgres, неотправленные сообщения ждут в очереди на клиенте, есть индикаторы набора и прочтения. Безопасность: личные чаты только после взаимного добавления в друзья, жалоба и блокировка, у детей — только чат команды.

В фундамент добавляется один слой реального времени на всё: чат, уведомления в приложении и прогресс команды идут по одному WebSocket-соединению.

## Что идёт параллельно всем этапам

Самая большая работа проекта — не код, а контент. Он должен идти постоянным потоком с этапа 1, иначе готовый движок будет стоять пустым.

- **Производство контента.** Я пишу черновики KC, заданий и объяснений в Nickel, ты вычитываешь (узбекский — обязательно). Реалистичный темп: 3–5 KC в неделю с 20+ заданиями на каждую.
- **Ревью нераспознанных ответов.** Раз в неделю разбирать очередь: добавлять в допустимые или в ожидаемые ошибки.
- **Реальные ученики с первого этапа.** Братья и сестры пользуются каждой готовой частью; их логи — единственный способ проверить модель.
- **Технический долг.** Последняя неделя каждого этапа — только рефакторинг и тесты, без новых функций.

## Открытые вопросы

1. **Интерфейс: SolidJS или Leptos.** Leptos — фреймворк на Rust, тогда весь проект на одном языке. Но у него меньше готовых решений для PWA и аудио, и бандл тяжелее. Решено: SolidJS (TypeScript), вся логика в Rust.
2. **Вход в аккаунт.** Решено: оба способа. Один аккаунт, к которому можно привязать и почту, и Telegram: способы входа хранятся отдельно от пользователя.
3. **Где хостить.** Сервер в Eskiz или домашний стенд; нужно уточнить ресурсы под LanguageTool (около 1–2 ГБ RAM).
4. **Для кого первая версия.** Только семья или сразу открытая регистрация. От этого зависят защита от спама, политика конфиденциальности и нагрузка.
