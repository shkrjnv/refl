# Синхронизация, версии и эксплуатация

Nov 24, 2026 · @Hara

## Зачем

Offline-first (docs/01) обещает, что ученик занимается без интернета, а сервер и устройство считают одинаково. Это держится на трёх вещах, которые до этого документа были описаны одной строкой: протокол синхронизации, правила для разных версий клиента, ядра и контента и хранение на устройстве. Здесь они описаны полностью, плюс эксплуатация: бэкапы, восстановление, выкатка.

## Что уже решено (docs/01, docs/02)

- События создаются на устройстве с UUIDv7; лог только дописывается; повторная вставка того же event\_id игнорируется — синхронизация идемпотентна.
- Свёртка идёт в порядке event\_id одинаково везде; событие, пришедшее позже, встаёт на своё место, снапшот с позицией больше его event\_id пересчитывается.
- Свёртка не перепроверяет ответы: вердикт записан в событии, исправления приходят событием `reclassified`. Поэтому для свёртки не нужен тот контент, с которым ответ проверялся.
- Сервер проверяет событие типами ядра (`decode_event`) и хранит его как прислано.

## Протокол синхронизации

Один эндпоинт, двусторонний обмен пакетами.

```
POST /v1/sync
  → { learner_id, core_version, content_version, cursor, events: [≤ 500] }
  ← { accepted: [event_id], rejected: [{event_id, reason}],
      events: [≤ 500], cursor, more: bool,
      server_time, min_core_version, latest_content_version }
```

- **Отправка.** Клиент шлёт неотправленные события пакетами до 500, по возрастанию event\_id. Событие считается отправленным, когда его event\_id пришёл в `accepted` или `rejected`.
- **Получение.** У каждой записи в базе есть `server_seq` — монотонный номер вставки (отдельно от event\_id: event\_id задаёт порядок свёртки, `server_seq` — порядок получения). `cursor` — последний `server_seq`, который клиент уже получил. Сервер отдаёт события ученика с `server_seq` больше курсора: созданные на других устройствах, производные (вехи, ачивки, разблокировки), `reclassified`. `more = true` — повторить запрос.
- **Порядок `server_seq`.** Каждая вставка в лог одного ученика — пакет синхронизации, производные события, `reclassified` — идёт в транзакции, которая первым делом берёт `pg_advisory_xact_lock` по learner\_id. Причина: identity выдаёт номер при вставке, а не при фиксации. Без блокировки две параллельные транзакции одного ученика могут зафиксироваться в обратном порядке номеров, и клиент, чей курсор уже прошёл больший номер, никогда не получит меньший. С блокировкой транзакции одного ученика идут по очереди, и порядок фиксации совпадает с порядком `server_seq`. Разные ученики друг друга не ждут.
- **Отказы.** `rejected` с причиной: не тот ученик, неверная схема, событие из будущего (client\_ts больше server\_time более чем на сутки). Отклонённое событие не удаляется с устройства, а помечается и показывается в отладке; ученику — «часть данных не синхронизировалась», с отправкой отчёта.
- **Когда синхронизироваться:** при запуске, после каждой сессии, при появлении сети и не чаще раза в 30 секунд во время занятия. Занятие от синхронизации не зависит.
- **Атомарность.** Пакет вставляется в одной транзакции; обрыв связи посреди обмена безопасен: повтор отправит те же события, сервер их проигнорирует.

### Время устройства

UUIDv7 и client\_ts берутся с часов устройства, а они бывают неверны. Сервер возвращает `server_time`; клиент хранит смещение (server\_time − локальное время в момент ответа) и с этого момента создаёт event\_id и client\_ts по исправленному времени. Смещение больше суток — предупреждение «на устройстве неверное время». Уже созданные события не переписываются: порядок свёртки остаётся детерминированным, а модель берёт интервалы из client\_ts, исправленных смещением, которое было известно при создании события.

### Вход и токены

- Короткий токен доступа (15 минут) и токен обновления на 90 дней, продлевающийся при каждой синхронизации. Занятия офлайн токена не требуют: события пишутся локально.
- Токен обновления истёк — нужен вход; локальные события сохраняются и отправляются после входа.
- Хранилище на устройстве разделено по learner\_id. Если на устройстве входит другой ученик, данные первого не смешиваются и не видны; выход из аккаунта предлагает удалить локальные данные этого ученика (неотправленные события сначала отправляются).
- Стирание аккаунта (docs/02): сервер отвечает на синхронизацию `erased`, клиент удаляет все локальные данные этого ученика.

## Три версии и их несовпадение

| Версия | Что меняет | Где записана |
| --- | --- | --- |
| схема событий (`schema_version`) | формат событий | в каждом событии |
| ядро (`core_version`) | код ядра: свёртка, проверка, нормализация, планировщик; включает версию модели и её параметры | в клиенте, в снапшоте |
| контент (`content_version`) | бандл: задания, шаблоны, граф | в клиенте, в событии ответа через ItemRef |

### Изменение схемы событий

Старое ядро должно либо прочитать событие правильно, либо увидеть его неизвестным, но никогда не прочитать неверно. Отсюда правило:

- **без новой версии схемы** добавляются только новые типы событий и новые варианты `Response`. Старое ядро узнаёт их по тегу (`type`, `response.kind`) и сохраняет как неизвестные;
- **любое другое изменение** — новое значение перечисления внутри существующего события, новое обязательное поле, изменённый смысл поля — повышает `schema_version`. Старое ядро видит такое событие неизвестным по версии, а сервер и новое ядро поднимают старые версии до текущей через upcasters.

Целые числа в событиях не больше 2⁵³ − 1 (docs/02, «Событие и лог»): событие должно читаться клиентом на JavaScript без потери точности.

### Неизвестные события

Устройство с ядром старше может получить событие, которое создал более новый клиент на другом устройстве, — новый тип события или новый вариант `Response`.

1. Ядро не отбрасывает и не угадывает: событие сохраняется на устройстве как есть (JSON), со своим event\_id.
2. Свёртка пропускает его и помечает состояние как **неполное** (флаг в состоянии).
3. Интерфейс показывает «обновите приложение, чтобы увидеть всё» — без блокировки занятий: ученик продолжает учиться, его собственные события создаются ядром, которое он понимает.
4. После обновления ядра — полный пересчёт со всеми сохранёнными событиями.

Это правило для пункта очереди «неизвестные события у старых клиентов»; `decode_event` получает отдельный результат «неизвестное событие, сохранить без свёртки» вместо ошибки.

### Минимальная версия ядра

Сервер объявляет `min_core_version`. Клиент ниже неё может заниматься офлайн, но синхронизация отклоняет его события, пока он не обновится. Минимальная версия поднимается только при несовместимых изменениях: новая схема событий, исправление ошибки проверки, из-за которой старые клиенты пишут неверные вердикты.

### Обновление приложения

- PWA проверяет обновление при запуске и при синхронизации.
- **Обновление применяется только между сессиями**, никогда посреди занятия: смена ядра посреди сессии сломала бы план и время ответов.
- Новое ядро с новой версией модели → полный пересчёт состояния на устройстве в Web Worker. Бюджет: одно событие — микросекунды, год занятий — доли секунды; если дольше секунды, показывается прогресс.
- Новый контент скачивается целиком по версии (бандл сжат; для этапа 1 — сотни килобайт), а аудио — по мере надобности. Ответы, данные до обновления, остаются со своими вердиктами; серверная перепроверка дописывает `reclassified`.

### Совместимость API

Эндпоинты версионированы (`/v1`). Внутри версии изменения только добавляющие: новые необязательные поля, новые эндпоинты. Удаление или изменение смысла поля — `/v2`, и сервер держит `/v1`, пока ниже `min_core_version` не останется клиентов.

## Хранение на устройстве

**Что хранится (IndexedDB, по ученику):**

- снапшот состояния текущей версии модели + его позиция;
- события после позиции снапшота;
- неотправленные события (всегда, пока не отправлены);
- сохранённые неизвестные события;
- текущий бандл контента;
- кэш аудио с вытеснением по давности (LRU).

**Сжатие лога на устройстве.** События, которые сервер подтвердил и которые уже вошли в снапшот текущей версии модели, с устройства удаляются. Полный лог живёт на сервере. Когда нужен весь лог (статистика «за всё время», пересчёт новой моделью) — он докачивается с сервера постранично; без сети показываются числа из снапшота с пометкой «на момент последней синхронизации».

**Бюджет:** до 50 МБ без аудио, аудио — до 200 МБ с вытеснением. Хранилище запрашивается как постоянное (`navigator.storage.persist()`); если браузер отказал, неотправленные события синхронизируются при первой возможности, а интерфейс предупреждает, что офлайн-данные могут быть очищены браузером.

## Несколько устройств

- События с разных устройств сливаются по event\_id; конфликтов нет.
- План сессии — производные данные устройства, а не общее состояние: каждое устройство строит свой план по своей свёртке. `plan_issued` с обоих устройств попадают в лог как есть.
- Одновременные сессии на двух устройствах разрешены. Правила, зависящие от порядка («первый ответ по KC за день считается для FSRS», docs/03), детерминированы порядком event\_id, поэтому после синхронизации обе стороны приходят к одному состоянию.

## Эксплуатация

| Что | Как | Цель |
| --- | --- | --- |
| бэкапы | pgBackRest: полный еженедельно, разностный ежедневно, непрерывная архивация WAL | потеря данных при аварии (RPO) — не больше 5 минут |
| проверка восстановления | ежемесячно, автоматически (таймер systemd в модуле NixOS): восстановление последнего бэкапа во временный кластер, пересчёт моделей нескольких случайных учеников, сравнение хэшей с рабочими снапшотами | восстановление, которое ни разу не проверяли, не считается бэкапом |
| время восстановления (RTO) | до 4 часов; клиенты всё это время занимаются офлайн | |
| миграции базы | только совместимые со старой версией сервера (добавить → перенести → удалить в следующем релизе) | откат сервера без отката базы |
| выкатка | новая версия NixOS-модуля, откат на предыдущее поколение одной командой | |
| мониторинг | ошибки синхронизации, доля отклонённых событий, отставание `server_seq`, клиенты ниже `min_core_version`, нарушения валидатора плана (docs/11) | |

## Что в схеме

- В таблице событий — `server_seq` (bigint, identity), индекс (learner\_id, server\_seq). Вставка — под блокировкой ученика (`pg_advisory_xact_lock`).
- `decode_event` различает «ошибка» и «неизвестный тип или вариант — сохранить без свёртки».
- В состоянии модели — флаг «неполное».
- Эндпоинт `/v1/sync` — с этапа 1.

## Открытые вопросы

1. **Push вместо опроса.** Когда появится WebSocket (чат, docs/01), события других устройств можно присылать сразу. До этого — синхронизация по событиям выше.
2. **Шифрование локальных данных** на общих устройствах (семейный планшет): нужен ли PIN на профиль ученика.
