# Сквозной прототип «Артикли»

Nov 24, 2026 · @Hara

## Зачем

Спецификация на этапы 0–1 достаточно полная; дальше её проверяет только работающий код. Прототип — первая версия, которую можно открыть на телефоне и пройти: одна тема, весь путь от контента до числа в статистике. Он проверяет стыки, где сейчас больше всего риска (контент → бандл → сервер → PWA → WASM → лог → синхронизация → свёртка), и даёт автору увидеть платформу, а не представлять её.

**Заморозка спеки.** Пока прототип не принят, docs/01–14 меняются только тогда, когда код показал проблему. Новые идеи записываются в открытые вопросы, а не в разделы.

## Состав темы «Артикли»

Пять KC. Деление — по критерию docs/02: любая ошибка на KC объясняется одним правилом. Поэтому выбор a или an по звуку — отдельная KC, а не часть «первого упоминания»: *a apple* и *I have cat* — разные ошибки с разным лечением.

| KC | Уровень | Правило |
| --- | --- | --- |
| `en.gram.noun.countability` | A1 | исчисляемые: a/an в единственном, -s после числа; неисчисляемые (water, advice, information, furniture, bread) — без a/an и без -s |
| `en.gram.article.a-an-sound` | A1 | an перед гласным звуком, a перед согласным; по звуку, а не по букве (an hour, a university) |
| `en.gram.article.first-mention` | A1 | исчисляемое в единственном числе при первом упоминании — с a/an |
| `en.gram.article.second-mention` | A1 | уже упомянутое или известное обоим — с the |
| `en.gram.article.zero-general` | A2 | множественное и неисчисляемое в значении «вообще» — без артикля (Cats are clever, I like music) |

**Рёбра.** requires: first-mention → countability, second-mention → first-mention, zero-general → countability. supports: a-an-sound помогает first-mention. contrasts: first-mention ↔ second-mention, zero-general ↔ second-mention; у каждого есть задания с `confuses_with`.

**Заблуждения** (10): пропуск артикля (L1), the для нового, a для уже упомянутого, a перед гласным звуком, a/an по букве, a/an с неисчисляемым, множественное у неисчисляемого, единственное после числа (L1 uz и ru: «uchta stul», «три стула»), the в общих утверждениях, a с множественным числом.

**Состав заданий** — только виды прототипа: выбор, поиск ошибки, ввод в пропуск. У каждой KC 11–16 live-заданий в 3–5 семьях, из них не меньше 6 вводов (производство), сложность покрывает 2–3 соседних уровня; семья — не больше 5 заданий. Поиск ошибки — там, где одно предложение однозначно содержит ровно одну ошибку в артикле или форме (countability, a-an-sound, second-mention); для first-mention и zero-general таких предложений без двусмысленности (*in a park* / *in the park*) не набирается, там выбор и ввод. У дистрактора поиска ошибки диагноз — заблуждение, при котором верный фрагмент кажется ошибкой.

**Языки.** en — окончательный текст; uz и ru пишутся сразу и до вычитки автором имеют `review = draft`. Статус live от `review` не зависит (docs/02, условия live), поэтому тема live до вычитки.

## Визуальный эталон

Интерфейс прототипа строится по артбордам, спроектированным вместе с автором на холсте «refl — направления дизайна»: копии HTML лежат в `design/reference/` (LiveToday, LiveMobile, LiveStats, StatsDeep — «Живая Студия»; ProfileMe, ProfileOther, Frames, ProfileV2, Wardrobe, Achievements, Deck — профиль). Это эталон стиля: палитра, шрифт Geologica, «объёмные» кнопки и плитки с плотной нижней тенью, один иллюстрированный блок на экран, прорисовка данных, движение.

docs/08 версии 2 для прототипа **не применяется**: автор пересматривает дизайн по ходу, глядя на работающее приложение. Экраны, которых нет на холсте (Занятие, Объяснение, Итог сессии, Настройки, первый вход), делаются в том же стиле по ближайшему эталону.

Токены «Живой Студии»: INK `#14213d`, BG `#f3f5fa`, BLUE `#2f6bff`, SUN `#ff9f43`, GREEN `#22b07d`, CORAL `#ff6b6b`, PURP `#7c5cff`; градиенты только внутри иллюстраций. Токены выносятся в один файл темы (docs/07, «темы — пакеты данных»), экраны берут только токены, а не цвета напрямую: так смена дизайна потом не трогает экраны.

## Планка «выглядит завершённым»

Прототип узкий, но не сырой. Каждый экран из объёма доведён до вида готового продукта:

- **ни одной заглушки:** нет lorem ipsum, «TODO», серых прямоугольников вместо иллюстраций, пустых кнопок; если функции нет, её нет и в интерфейсе;
- **все состояния:** загрузка, пусто, ошибка, офлайн, «ждёт синхронизации», первый раз и повторный визит; у каждого — свой текст и вид;
- **движение по эталону:** появление данных, отклик кнопок, переходы между шагами урока; при «уменьшить движение» — без анимаций;
- **телефон и компьютер:** проверено на ширине 360 и 1440 px; зоны нажатия от 44 px;
- **тексты по навыку `refl-writing`** (`.claude/skills/refl-writing/`): ни одной строки «как у ИИ»; все строки интерфейса через Fluent, на uz / ru / en; uz и ru — на вычитку автору;
- **иллюстрации:** векторные, в стиле эталонов; Iella — пиксельная (docs/06);
- **шрифты и ресурсы — свои:** Geologica и остальное отдаёт наш сервер, без Google Fonts и других CDN (эталоны грузят шрифт с Google — в приложении так нельзя: docs/14, никаких сторонних запросов);
- **скорость:** первая загрузка на среднем телефоне по 4G — до 3 секунд; JS без WASM — до 300 КБ gzip, WASM ядра — до 500 КБ gzip; ответ на задание — вердикт быстрее 50 мс.

## Первый вход с Iella

1. Знакомство (10–15 секунд): экран затемнён, подсвечена область Iella, она прилетает, одна реплика.
2. Экскурсия — не больше трёх остановок с подсветкой: маршрут на сегодня, уровень, кнопка «Начать».
3. Первое настоящее задание сразу после экскурсии — оно и есть знакомство с занятием.
4. Остальное — при первой встрече: элемент подсвечивается одной фразой Iella, когда ученик впервые его видит.
5. Пропуск в один тап на любом шаге, повтор из настроек; шаги пишутся в лог, чтобы видеть, где бросают.

## Критерии приёмки

Прототип принят, когда выполнено всё:

1. `just content` собирает бандл, в котором 4–6 KC темы «Артикли» в статусе live.
2. Сервер импортирует бандл, принимает и отдаёт события через `/v1/sync` (docs/13); повторная отправка не создаёт дублей.
3. На телефоне: установка PWA, вход, первый вход с Iella, урок по одной KC, сессия с повторениями на следующий день.
4. Режим полёта посреди урока: урок продолжается, события копятся, после включения сети синхронизируются; ни одно не потеряно.
5. Тот же ученик на втором устройстве видит то же состояние после синхронизации; хэши состояния модели на устройстве и на сервере совпадают при одной версии модели и одном `content_version`.
6. Статистика показывает освоенные KC, «в памяти» и калибровку прогноза, и каждое число объясняется подсказкой «откуда это» (docs/09).
7. Обновление приложения между сессиями с новой версией модели вызывает пересчёт на устройстве; посреди урока обновление не применяется.
8. Все экраны из объёма проходят планку «выглядит завершённым»; автор прошёл весь путь сам и записал замечания.
9. `just ci` зелёный: тесты ядра (включая native = WASM), сервера, клиента.

## Порядок работ

После пунктов 1–4 очереди агента (переименование, неизвестные события, изменения схемы, граница предмета):

1. Ядро: модель ученика v1 и свёртка, FSRS-6, автоматизм, заблуждения, быстрые попытки; простая сборка сессии.
2. Контент «Артикли» до live (черновики — Claude по навыку `refl-writing`, вычитка — автор).
3. Сервер: `/v1/sync`, вход по коду, `server_seq`.
4. Клиент: каркас PWA, IndexedDB, WASM-ядро в Web Worker, тема по токенам.
5. Экраны по эталонам, первый вход с Iella.
6. Проход по критериям приёмки, правки.
