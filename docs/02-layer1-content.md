# Спецификация: слой 1 — контент и данные

Nov 21, 2026 · @Hara

## Назначение и принципы

Слой 1 определяет, какие данные хранит платформа: единицы знания, заблуждения, задания, объяснения, уроки и события. Модель ученика (слой 2), placement (слой 3) и планировщик (слой 4) только читают эти данные и ничего в них не меняют.

Принципы:

1. **Задание не зависит от языка интерфейса.** Английское содержимое хранится отдельно от объяснений на uz/ru/en.
2. **Контент живёт как код.** Задания, объяснения и граф лежат текстовыми файлами в git, проходят проверку при сборке и загружаются в БД. Так каждая правка видна в истории и её можно откатить.
3. **Лог событий неизменяем.** Всё, что система знает об ученике, выводится из этого лога. Исправления добавляются новыми событиями, старые не переписываются.
4. **Каждое событие ссылается на конкретную версию задания.** Правка задания не ломает старую статистику.
5. **Проверка ответов детерминированная.** Правила, списки допустимых ответов и локальные инструменты (Hunspell, LanguageTool), без внешних ИИ-сервисов.
6. **Глубина важнее объёма.** Ни одно задание не попадает в банк без привязки к единицам знания и без диагностических дистракторов или шаблонов ошибок.

Сюда не входят: формулы модели ученика, логика placement, планировщик сессий и интерфейс.

## Единица знания и граф

Единица знания (KC) — наименьшее правило, которое можно знать или не знать. Критерий гранулярности: на KC можно сделать 10+ разных заданий, и любая ошибка на нём объясняется одним правилом. Артикли дают 5–8 KC, вся грамматика A1–C1 ориентировочно 300–500 KC.

| Поле | Тип | Зачем |
| --- | --- | --- |
| id | слаг, напр. `gram.article.first-mention` | стабильная ссылка, не меняется никогда |
| domain | grammar, phonology, orthography, discourse, reading-skill, listening-skill, writing-skill | для фильтров и баланса сессии |
| title | uz / ru / en | название для ученика |
| cefr | pre-A1 … C2 | уровень, на котором правило обычно осваивают |
| importance | 0–1 | частотность конструкции × вес для цели; вход планировщика |
| rule | короткая формулировка | для автора контента, не для ученика |
| tags | список | напр. `ielts-relevant`, `l1-hard-uz` |

**Статус KC — live или draft — вычисляет content-build, автор его не задаёт.** Планировщику нужны задание на производство и разброс сложности, поэтому одного числа заданий мало. KC получает live, только если у неё есть объяснение глубины short хотя бы на ru и en (why и deep желательны, но live не блокируют), и среди live-заданий, где она primary хотя бы в одном слоте:

- ≥ 10 заданий;
- ≥ 3 семьи;
- ≥ 3 задания на производство: для освоения нужны 2 верных без повторов (docs/03), плюс запас. На производство считаются ввод в пропуск, трансформация, перевод, своё предложение и writing (`gap_fill`, `transformation`, `translation`, `own_sentence`, `writing`). Диктант и сборка предложения не считаются: в них нет самостоятельного производства формы;
- сложность (рубрика 1–5) покрывает минимум 2 соседних уровня.

Если условие не выполнено, KC остаётся draft, и content-build пишет в отчёт, чего не хватает. Сборка при этом не падает.

Live-задание, у которого хотя бы одна primary KC в статусе draft, в сессии не попадает, пока все его primary KC не станут live; content-build вычисляет этот признак и кладёт его в бандл. В условиях live своей KC такое задание учитывается, иначе KC никогда не стала бы live.

Рёбра графа, четыре типа:

- **requires** — жёсткий пререквизит: без него тему не дают. Граф по этим рёбрам ацикличен, сборка это проверяет.
- **supports** — мягкая связь: помогает, но не обязательна.
- **contrasts** — темы, которые путают (Present Perfect ↔ Past Simple). Планировщик смешивает их в практике (interleaving).
- **part\_of** — иерархия KC → тема → раздел, для навигации и карты знаний.

Если ученик ошибается в «a/an: первое упоминание», планировщик сначала проверяет пререквизит «Исчисляемые и неисчисляемые»: корень ошибки часто там.

**Лексика моделируется отдельно.** Единица лексики — значение слова (word sense) с частотным рангом, формами и аудио. Если сделать каждое слово узлом графа, он раздуется до десятков тысяч узлов без пререквизитов. Слова отслеживаются через FSRS, а не через граф.

## Заблуждение

Заблуждение — устойчивая неверная идея, из которой рождаются предсказуемые ошибки. Именно оно, а не факт ошибки, превращает «неверно» в диагноз.

| Поле | Тип | Зачем |
| --- | --- | --- |
| id | слаг, напр. `mis.article.omission-l1` | стабильная ссылка |
| title | uz / ru / en | короткое имя для ученика и отчёта |
| affects | список KC | каким единицам знания оно вредит |
| origin | l1-transfer, overgeneralization, form-confusion, spelling-based | природа ошибки, определяет тип объяснения |
| l1 | uz, ru, оба или ни одного | для переноса из родного языка |
| prior | частота у носителей uz и ru, 0–1 | placement проверяет частые заблуждения первыми |
| remedy | KC | тема, которая лечит причину; обычно пререквизит |

Заблуждение распознаётся двумя путями: через выбранный дистрактор и через шаблон ожидаемой ошибки в свободном вводе (см. проверку ответов). Один и тот же id приходит из обоих источников, поэтому статистика складывается.

**Микро-объяснение** после ошибки отдельным полем не задаётся: оно находится по ключу — объяснение с target = это заблуждение и depth = short, язык по цепочке «язык интерфейса → ru → en» (раздел «Объяснение»). Заблуждение считается live, если его может диагностировать хотя бы одно live-задание (через дистрактор или шаблон ошибки); у каждого live-заблуждения обязано быть short-объяснение на ru и на en, иначе ошибка сборки: ученик остался бы без обратной связи.

## Задание: общая часть

Единица оценивания — не задание, а его пропуск (слот). В истории с 6 пропусками шесть независимых ответов, у каждого свои KC, свои дистракторы и своё событие в логе.

**Задание:**

| Поле | Тип | Зачем |
| --- | --- | --- |
| id, version | слаг + целое | событие ссылается на пару |
| family | слаг | семья вариантов одного задания, делят оценку сложности |
| type | см. типы заданий | определяет интерфейс и проверку |
| instruction | ссылка на инструкцию | инструкции переведены один раз, а не в каждом задании |
| stimulus | английский текст с метками пропусков, аудио, картинка | само задание |
| slots | список | см. ниже |
| difficulty | приор автора + калибровка | сначала экспертно, потом из данных |
| expected\_time | секунды | для оценки автоматизма и планирования сессии |
| topic | travel, tech, family… | тема содержания, чтобы подбирать интересное |
| status | draft, review, live, retired | в сессии попадает только live |
| case\_sensitive | флаг, по умолчанию нет | для заданий на заглавные буквы |
| contractions | strict (по умолчанию) или equivalent | strict: проверяется именно don't vs do not; equivalent: обе стороны раскрываются по фиксированной таблице |
| punctuation\_sensitive | флаг, по умолчанию нет | пунктуация участвует в сравнении |
| source, license | текст | откуда взят текст, если не свой |

**Пропуск (slot):**

| Поле | Зачем |
| --- | --- |
| kcs | KC с весом: primary (проверяется прямо) или secondary (нужна, но не цель). Это и есть Q-матрица |
| answer | эталонный ответ: его видит ученик как правильный; должен приниматься шаблоном accepted |
| accepted | допустимые ответы, можно шаблоном |
| options | для выбора: вариант → заблуждение или `null` (шум) |
| expected\_wrong | для ввода: шаблон ошибки → заблуждение; порядок значим, первое совпадение выигрывает |
| hint | необязательная подсказка, её использование пишется в лог |
| why | объяснение правильного ответа в этом конкретном предложении |

Правило качества, проверяемое при сборке для каждого слота live-задания:

- **выбор** (`choice`, `find_error`): минимум 2 дистрактора с диагнозом. `options` — только неверные варианты, правильный вариант — `answer`. Ни один дистрактор не принимается шаблоном `accepted`, и дистракторы не повторяются (сравнение в нормализованном пространстве);
- **ввод** (`gap_fill`, `transformation`, `translation`, `dictation`, `sentence_assembly`): минимум 2 шаблона ожидаемых ошибок;
- остальные типы (`matching`, `true_false_not_given`, `own_sentence`, `writing`, `shadowing`) в статусе live — ошибка сборки, пока этап, который их вводит, не определит для них правило.

**Инструкция** — отдельная сущность контента: id (слаг) и текст на uz / ru / en. У инструкции, на которую ссылается live-задание, обязательны ru и en (та же цепочка «язык интерфейса → ru → en», что у объяснений); uz добавляется после вычитки.

**Семьи заданий.** Чтобы получить 40–60 вариантов на тему, не пишем каждое с нуля: одна семья = одна конструкция с разными предложениями. При повторении ученик получает другого члена семьи, и система проверяет правило, а не память на конкретное предложение.

## Типы заданий

Задания идут по лестнице: узнавание → управляемое производство → свободное производство. KC считается освоенным, только когда есть успехи на уровне производства: узнавание систематически переоценивает знание.

| Тип | Уровень | Проверка |
| --- | --- | --- |
| Выбор варианта | узнавание | авто, дистрактор → диагноз |
| Поиск ошибки | узнавание | авто |
| Сопоставление (в т.ч. IELTS matching headings) | узнавание | авто |
| True / False / Not Given | узнавание | авто |
| Ввод в пропуск, с базовой формой или без | управляемое | нормализация + допустимые варианты + шаблоны ошибок |
| Трансформация («перепиши, используя since») | управляемое | шаблоны допустимых ответов |
| Сборка предложения из слов | управляемое | список допустимых порядков |
| Перевод коротких предложений uz/ru → en | управляемое | шаблоны допустимых переводов + классификация ошибок; самый трудоёмкий в авторстве |
| Диктант (аудио → текст) | управляемое | выравнивание с эталоном + типы ошибок (слабые формы, связки слов) |
| Своё предложение по заданию | свободное | авто: наличие целевой конструкции, орфография, LanguageTool; смысл: самооценка по чеклисту или ментор |
| Writing: письмо, эссе, IELTS Task 1/2 | свободное | метрики (длина, связки, лексическое разнообразие, LanguageTool) + чеклист по критериям + образец + ментор |
| Shadowing | произношение | фаза 2: сравнение интонации и ритма через DSP |

**Контейнер «пассаж».** Reading и listening — это текст или аудио с вложенными заданиями любого типа из таблицы. У пассажа свои поля: длина, уровень по лексическому покрытию, тайминг, транскрипт для аудио, акцент диктора. IELTS-секция — тот же пассаж с жёстким таймингом и пересчётом в band.

## Проверка ответов на ввод

Проверка идёт конвейером из пяти шагов и всегда выдаёт один из четырёх вердиктов: верно, опечатка, ошибка (с диагнозом или без), не распознано.

1. **Нормализация** — по правилам раздела «Язык шаблонов ответов» ниже, одинаково к ответу и к литералам шаблона. Британское и американское написание (colour = color) приравниваются по фиксированной таблице. В нормализации v1 этой таблицы нет: она появится с лексикой на этапе 3 (нужны все формы слов и исключения вроде practise/practice) и поднимет версию нормализации.
2. **Сравнение с допустимыми ответами.** Ответы пишутся на маленьком языке шаблонов: альтернативы `(I have|I've) been`, необязательные части `[already]`. Шаблон компилируется в автомат, проверка точная и быстрая.
3. **Сравнение с ожидаемыми ошибками.** Те же шаблоны, но каждый привязан к заблуждению: `have went` → путаница форм глагола.
4. **Выравнивание с ближайшим правильным.** Расстояние Левенштейна по словам, затем классификация расхождения:
   - опечатка: 1–2 символа внутри слова, и результат не другое слово словаря;
   - другая форма того же слова (лемма та же): грамматическая ошибка;
   - пропущенное или лишнее слово (часто артикль, предлог, вспомогательный глагол);
   - неверный порядок слов.
5. **Не распознано.** Ответ засчитывается как неверный без диагноза, ученик может нажать «мой ответ тоже верный». Ответ уходит в очередь на ревью, автор добавляет его в допустимые или в ожидаемые ошибки, и старые события переклассифицируются.

### Язык шаблонов ответов

**Нормализация** — одна версионированная функция в core. Она применяется до сравнения, одинаково к ответу и к литералам шаблона:

- NFC; варианты апострофа и кавычек приводятся к ASCII; пробелы схлопываются; trim.
- Регистр не учитывается по умолчанию. Флаг задания `case_sensitive` — для заданий на заглавные буквы.
- Сокращения по умолчанию НЕ раскрываются: в части заданий проверяется именно don't vs do not. Флаг задания `contractions = "equivalent"` раскрывает обе стороны по фиксированной таблице (ниже).
- Пунктуация — отдельные токены, по умолчанию игнорируется. Флаг `punctuation_sensitive`.
- Апостроф в конце слова — пунктуация (см. «Токены»), поэтому при настройках по умолчанию `dogs'` = `dogs`. Задания на притяжательный падеж обязаны ставить `punctuation_sensitive`.
- Изменение таблиц нормализации = новая версия контента → перепроверка и `reclassified` (раздел «Событие и лог»).

**Таблица сокращений** для `contractions = "equivalent"`. В неё входят только однозначные сокращения:

| Сокращение | Раскрытие |
| --- | --- |
| don't, doesn't, didn't, isn't, aren't, wasn't, weren't, haven't, hasn't, hadn't, wouldn't, couldn't, shouldn't, mustn't, needn't, mightn't | do not, does not, … (основа + not) |
| won't | will not |
| shan't | shall not |
| can't | can not |
| I'm | I am |
| you're, we're, they're | you are, we are, they are |
| I've, you've, we've, they've, could've, should've, would've, might've, must've | I have, … (основа + have) |
| I'll, you'll, he'll, she'll, it'll, we'll, they'll | I will, … (основа + will) |

- Не входят: `'s` (is, has или притяжательный), `'d` (had или would), `ain't`, `let's`.
- `cannot` в таблице нет и с `can't` не совпадает.
- Сокращение распознаётся без учёта регистра. При `case_sensitive` регистр первой буквы переходит на первое слово раскрытия: `Don't` → `Do not`, `I'm` → `I am`.

**Токены.** Слово — непрерывная последовательность букв, цифр, апострофов и дефисов внутри слова. Пунктуация — отдельный токен.

**Грамматика (EBNF):**

```
pattern := seq
seq     := elem*
elem    := word | group | option
group   := "(" seq ("|" seq)+ ")"
option  := "[" seq "]"
word    := (char | "\" special)+
special := "(" | ")" | "[" | "]" | "|" | "\"
```

- Альтернативы — это последовательности слов, а не подстроки: `(a|an) apple` можно, `walk(s|ed)` нельзя, пиши `(walks|walked)`. Так токенизация остаётся однозначной.
- Слово вплотную к группе или опции (без пробела) — ошибка: `walk(s|ed)`, `(John|Mary)'s`. Исключение — слово только из пунктуации: `(John|Mary).` можно, точка всё равно отдельный токен.
- Пустая альтернатива `(a|)` запрещена, для этого есть `[a]`. То же после нормализации с флагами задания: альтернатива, опция или шаблон целиком, которые могут совпасть с пустой строкой, — ошибка сборки (`(a|[b])`, `[already]` как весь шаблон, `(a|.)` при игнорируемой пунктуации).
- Вложенность разрешена, глубина ≤ 4. Глубже — ошибка сборки: такой шаблон уже не прочитать.
- Повторений (`*`, `+`) нет. Значит, язык шаблона всегда конечен. Это сознательное ограничение.
- Компиляция — в DFA над алфавитом интернированных токенов плюс символ OTHER.

Шаг 5 — главный механизм роста качества: с каждым реальным ответом банк допустимых ответов и ошибок становится полнее.

**Опечатка не наказывает грамматику.** Она обновляет KC орфографии, а целевой KC задания считается сданным. Иначе система будет путать незнание правила с невнимательностью.

Локальные инструменты: словари Hunspell (en-GB, en-US), таблицы форм слов (неправильные глаголы, множественное число), LanguageTool как локальный сервер — только для свободного письма.

## Объяснение

Объяснений два вида: полное привязано к KC, микро-объяснение (до 2 предложений) привязано к заблуждению и показывается сразу после ошибки.

| Поле | Зачем |
| --- | --- |
| target | KC или заблуждение |
| depth | short, why, deep — три уровня, как в демо |
| lang | uz, ru, en; каждый язык — отдельная запись |
| body | markdown + набор компонентов: пример с аудио, таблица, дерево решений, линия времени |
| l1\_contrast | отдельный блок для uz и для ru |
| examples | английские предложения с аудио, общие для всех языков |
| review | статус перевода: draft или reviewed, кем проверено |

**Контраст с родным языком — не перевод.** Узбекский блок объясняет через *bir* и *-ni*, русский через порядок слов. Это разные тексты, и авторить их нужно отдельно. Остальное объяснение переводится.

**Запасной язык.** Если нужной записи нет: язык интерфейса → ru → en. С уровня B2 по умолчанию показывается en, родной доступен по нажатию. Каждый просмотр объяснения (какой уровень, сколько секунд) пишется в лог.

## Урок и шаги

Урок — упорядоченный набор шагов по набору KC. Шаги практики ссылаются не на конкретные задания, а на запрос к банку, поэтому новые задания автоматически попадают в урок, а планировщик может подбирать их адаптивно.

| Шаг | Содержимое |
| --- | --- |
| pretest | попытка до объяснения (productive failure); ответы обновляют модель без «обучения» |
| explanation | ссылка на объяснение KC, начальный уровень глубины |
| worked\_examples | разобранные примеры с аудио |
| practice | запрос: KC + типы + диапазон сложности + число заданий; порядок от узнавания к производству |
| production | свободное производство по теме |
| posttest | повтор pretest или члены тех же семей заданий |
| summary | итог от модели: освоение, заблуждения, следующий шаг |

Урок — стартовая точка для новой темы, а не единственный путь. Повторения и точечная прокачка собираются планировщиком прямо из банка, без уроков.

## Событие и лог

Лог — единственный источник правды об ученике. Состояние модели — свёртка (fold) по событиям; снапшоты только ускоряют пересчёт и могут быть удалены в любой момент.

**Порядок свёртки** — по event_id (UUIDv7), одинаково на клиенте и на сервере, поэтому их состояния совпадают. Событие, пришедшее при синхронизации позже, встаёт на своё место по event_id.

**Снапшот** — ключ (ученик, версия модели), чтобы у теневых моделей были свои. Хранит состояние байтами в формате, который определяет версия модели (смена формата = новая версия и полный пересчёт), параметры модели (JSON и их хэш) и позицию — наибольший свёрнутый event_id. Пришло событие с event_id меньше позиции снапшота — снапшот устарел и пересчитывается.

**Лог в базе.** Таблица событий только дописывается: UPDATE, DELETE и TRUNCATE отклоняет сама база (триггер), а роль приложения имеет на неё только SELECT и INSERT. event_id уникален, повторная вставка того же события молча игнорируется — так синхронизация идемпотентна. Перед записью событие проверяется типами ядра (`decode_event`, с upcasters); хранится как прислано, со своим `schema_version`, и поднимается до текущей версии при чтении.

**Удаление аккаунта** — единственное исключение из «только дописывается». Одна функция базы удаляет все события и снапшоты одного ученика целиком и записывает факт удаления (id ученика и время, без личных данных) в журнал удалений. Функция принадлежит владельцу схемы, выполнять её может только отдельная роль удаления, а не роль приложения. Частичная правка лога по-прежнему невозможна. Роли кластера (приложение, удаление) миграция создаёт, если их нет; при откате миграций они не удаляются, потому что принадлежат кластеру, а не базе.

**Событие ответа:**

| Поле | Зачем |
| --- | --- |
| event\_id | UUIDv7: упорядочен по времени, создаётся на клиенте, поэтому офлайн-синхронизация идемпотентна |
| learner\_id, session\_id | чей и в какой сессии |
| client\_ts, server\_ts | время на устройстве и время приёма |
| item\_id, version, slot | точно что было показано |
| context | lesson, review, placement, practice, mock |
| response | сырой ответ: вариант или введённый текст как есть |
| verdict, misconception | результат проверки на момент ответа |
| latency\_ms | от показа до ответа; вход для оценки автоматизма |
| backgrounded | приложение уходило в фон во время задания: время ответа не учитывается (слой 2, «Автоматизм») |
| confidence | sure, unsure или пусто |
| hints, attempt | подсказки и номер попытки |

Другие типы событий: начало и конец урока, просмотр объяснения (уровень, секунды), проигрывание аудио, чтение текста из библиотеки, клик по слову.

**Переклассификация.** Когда автор добавляет ответ в допустимые, старое событие не меняется: добавляется событие `reclassified` со ссылкой на него, и модель ученика пересчитывается.

Кто и когда порождает `reclassified`: при каждом выкате новой версии контента, в которой изменились допустимые ответы или шаблоны ошибок, серверная задача перепроверяет затронутые ответы (тех слотов, где изменились шаблоны) текущей версией контента и для каждого изменившегося вердикта или заблуждения дописывает событие `reclassified` со ссылкой на исходное событие, новым вердиктом и версией контента. Fold никогда не перепроверяет ответы сам: он только применяет события. Поэтому результат свёртки зависит только от лога, а не от того, какой контент загружен на устройстве.

## Идентификаторы и версии

KC и заблуждения имеют читаемые слаги, которые не меняются; переименование = новый id + старый помечен как псевдоним. Задания имеют id семьи, id задания и номер версии.

Когда повышается версия задания:

- **да:** изменились стимул, варианты, правильный ответ или привязка к KC;
- **нет:** исправлена опечатка в объяснении, добавлен допустимый ответ или шаблон ошибки (это идёт через переклассификацию).

У новой версии флаг `breaks_calibration`: если изменение меняет сложность, статистика старой версии не переносится.

**Проверки при сборке контента** (запускаются на каждый коммит):

- все ссылки на KC, заблуждения и объяснения существуют;
- у каждого live-заблуждения есть short-объяснение на ru и на en (раздел «Заблуждение»);
- все ссылки на инструкции существуют; у инструкций live-заданий есть текст на ru и en;
- граф по рёбрам `requires` ацикличен;
- у каждого live-задания есть минимум диагностических дистракторов или шаблонов;
- статус каждой KC вычислен по условиям live (раздел «Единица знания и граф»); не выполненные условия перечислены в отчёте, сборка не падает;
- шаблоны ответов разбираются и компилируются (глубина вложенности ≤ 4);
- пересечения шаблонов проверяются точно, через произведение DFA (языки конечны), в нормализованном пространстве и с флагами конкретного задания; проверки на примерах не делаем:
    - допустимые ∩ каждый шаблон ошибки = ∅, иначе ошибка сборки с примером-свидетелем (кратчайшая строка из пересечения);
    - эталонный ответ слота принимается шаблоном допустимых, иначе ошибка;
    - шаблоны ошибок попарно: при пересечении — предупреждение со свидетелем; классификация идёт по порядку шаблонов, первое совпадение выигрывает;
- аудиофайлы, на которые есть ссылки, существуют (корень аудио по умолчанию `content/audio`).

Результат сборки — один JSON-бандл: KC с вычисленным статусом, рёбра, транзитивное замыкание `requires`, задания с признаком «можно давать в сессии», индексы заданий по KC, скомпилированные автоматы и версия нормализации. Все коллекции отсортированы. **Версия контента** — SHA-256 содержимого бандла: одинаковый контент даёт одинаковую версию и одинаковые байты, любое изменение, включая версию нормализации, даёт новую.

## Открытые решения

Семь вопросов нужно закрыть до старта реализации. Рядом с каждым — моя рекомендация.

1. **Формат файлов контента.** JSON + JSON Schema, TOML или типизированный язык конфигураций (Nickel, Dhall). Рекомендация: Nickel — принято. Цепочка: Nickel → экспорт в JSON → проверка Rust-типами при сборке → БД. Функции дают семьи заданий без копипасты. Риск привязки низкий: всё можно один раз выгрузить в JSON и продолжить без Nickel.
2. **«Пишет от руки».** Решено: имелся в виду самостоятельный ввод с клавиатуры, он уже в типах заданий. Рукописный ввод стилусом не делаем.
3. **Шкала сложности.** Автор ставит 1–5, система переводит в логиты IRT. Так удобно размечать и не нужно переделывать потом.
4. **Лексика отдельно от графа.** Нужно подтвердить; детали лексической модели — отдельный раздел.
5. **Акценты в аудио.** Старт с британского и американского, поле «акцент» заложить сразу.
6. **Лицензии словарей и корпусов.** Данные под CC BY-SA (например, из Викисловаря) обязывают распространять производное под той же лицензией. Нужно решить, что из данных платформы открыто.
7. **Объём старта.** Рекомендация: грамматика A1–B1, около 120–150 KC, по 20+ заданий на KC. Это уже 3000+ заданий, поэтому семьи заданий и авторские инструменты обязательны.
