# Предметы: граница ядра, японский, математика

Nov 24, 2026 · @Hara

## Зачем

Первый предмет — английский, и до конца этапа 2 он остаётся единственным, в который идёт контент. Но ядро с самого начала строится так, чтобы второй язык (японский) и математика добавлялись новыми модулями, а не переписыванием модели, планировщика и лога.

Критерий тот же, что в docs/01, «Фундамент с первого дня»: сейчас закладываем только то, что потом пришлось бы переделывать во всём коде или в уже записанных событиях. Сами модули японского и математики не пишутся до своих треков (docs/01, «Этапы»).

Методика предмета подстраивается через данные предмета — виды заданий, проверщик ввода, источники заблуждений, беглые задания, — и никогда через ветки по предмету в общем ядре (docs/00, принцип 11).

## Что зависит от предмета

Всё предметное собрано в слое 1 и в проверке ответа:

| Что | Сейчас (только английский) | Как становится |
| --- | --- | --- |
| шкала уровней | `Kc.cefr: Cefr` | шкала предмета, задаётся контентом |
| домены KC | закрытый enum `KcDomain` | список доменов предмета в контенте |
| виды заданий | закрытый enum `ItemType` с `match` по поведению | трейт `ItemKind`, данные — enum вариантов |
| проверка ввода | нормализация и токены английского, флаги `contractions`, `case_sensitive`, `punctuation_sensitive` прямо в `Item` | «проверщик» предмета со своей конфигурацией |
| лестница типов | узнавание → управляемое → свободное, жёстко по типам | ступень сообщает сам вид задания |
| лексика | значения слов, FSRS (этап 3) | лексический слой предмета: слова, кандзи, кана — карточки FSRS вне графа |

## Предмет

**Предмет** — запись контента: `id` (`en`, `ja`, `math`), название на uz / ru / en, шкала уровней, список доменов, проверщик ввода по умолчанию и KC орфографии (`spelling_kc`), которую обновляет опечатка (docs/02, «Проверка ответов на ввод»).

**Идентификаторы** KC, заблуждений и семей начинаются со слага предмета: `en.gram.article.first-mention`, `math.frac.add-unlike`. content-build проверяет префикс. Это меняет существующие слаги примера «Артикли»; пользователей ещё нет, поэтому меняем сейчас.

Рёбра графа между предметами разрешены только `supports` (например, математика → физика, если она появится). `requires` между предметами запрещено: иначе один предмет блокировал бы другой.

**Ученик** учит несколько предметов параллельно. Placement, общий уровень L и цель — у каждого предмета свои. Сессия собирается по одному предмету; общий дневной бюджет делит между предметами сам ученик.

## Шкала уровней

Шкала — упорядоченный список уровней с ключами и названиями, плюс шаг в логитах между соседними уровнями (для стартового μ, docs/03). В ядре уровень — ранг в шкале своего предмета; ключ (`B1`, `N4`, `g7`) остаётся для контента и интерфейса.

| Предмет | Шкала | Шаг (старт) |
| --- | --- | --: |
| английский | pre-A1, A1 … C2 | 1,2 |
| японский | pre-N5 (кана), N5 … N1 | 1,2 |
| математика | классы 1–11, затем вузовские треки | 0,8 (уровни мельче) |

У предмета ровно одна основная шкала. Пересчёт в другие шкалы (JLPT ↔ CEFR, класс ↔ международные программы) — только для отчётов, в модель не входит.

## Вид задания: трейт и данные

Поведение задаётся трейтом, данные — закрытым enum. Динамические плагины не нужны: serde, ts-rs и детерминизм требуют закрытых типов, а новый вид задания всё равно приходит с новой версией ядра.

```rust
pub trait ItemKind {
    /// Ступень лестницы: узнавание, управляемое, свободное, произношение.
    fn ladder(&self) -> LadderLevel;
    /// Считается ли верный ответ «производством» для критерия освоения (docs/03).
    fn is_production(&self) -> bool;
    /// Правило качества live-задания; проверяется content-build на каждый слот.
    fn quality(&self, ctx: &QualityCtx) -> Result<(), Vec<QualityIssue>>;
    /// Детерминированная проверка ответа одного слота.
    fn check(&self, slot: u16, response: &Response, ctx: &CheckCtx) -> CheckOutcome;
}
```

`Item` = общий заголовок (id, version, family, предмет, инструкция, сложность, expected\_time, статус, тема, источник, лицензия, `breaks_calibration`) + `body: ItemBody`. `ItemBody` — enum, по варианту на вид задания всех предметов; каждый вариант хранит свой стимул, слоты и настройки проверки и реализует `ItemKind`. Флаги английской нормализации переезжают из общего заголовка в настройки проверщика английских видов.

**Результат проверки** (`CheckOutcome`): либо «проверено» — вердикт и заблуждение, либо «не проверяется» — у вида пока нет автоматической проверки. Сейчас это matching, true\_false\_not\_given, own\_sentence, writing и shadowing: live они стать не могут, пока этап, который их вводит, не определит правило качества и проверку. Виды с выбором сравнивают канонический индекс варианта (docs/02, «Задание: общая часть»), английские виды на ввод идут по конвейеру ниже.

Новый вид задания = вариант `ItemBody` + реализация трейта + компонент отрисовки в реестре клиента. Модель, планировщик и лог не меняются.

## Проверщик ввода

Конвейер из docs/02 («Проверка ответов на ввод») остаётся общим: нормализация → допустимые → ожидаемые ошибки → выравнивание и классификация → не распознано. Вердикты те же четыре. Предмет поставляет три части конвейера:

| Часть | Английский | Японский | Математика |
| --- | --- | --- | --- |
| нормализация | docs/02 | NFKC, полуширинные формы → полноширинная кана, варианты `ー`, пунктуация `。、` как токены | разбор в выражение, канонизация |
| алфавит DFA | слова | символы (графемы) | не DFA: сравнение выражений |
| опечатка | 1–2 символа в слове, не другое слово словаря | промах IME: то же чтение, другой кандзи | в v1 нет |

Язык шаблонов ответов (`( | )`, `[ ]`) общий для английского и японского; различается только токенизатор. Для математики шаблоны не нужны: правильность определяется эквивалентностью и требованием к форме (ниже).

## Японский

Трек японского начинается, когда есть вычитывающий носитель: ни автор, ни Claude не могут гарантировать качество японского контента сами.

**Шкала и порядок.** pre-N5 — хирагана и катакана; дальше N5…N1. Кана и кандзи живут в лексическом слое (карточки FSRS, как значения слов в английском), а не в графе KC: тысячи кандзи раздули бы граф без пререквизитов. Грамматические пункты — KC графа.

**Ввод.** Ромадзи как ответ не принимается: после этапа каны ученик печатает через системную клавиатуру (IME). По умолчанию принимается и кана, и кандзи. Кандзи обязательны только в заданиях, где primary — навык кандзи; там промах IME (то же чтение, другой кандзи) — ошибка орфографии кандзи, а не грамматики.

**Разметка чтений.** Автор пишет японский текст с чтениями: `{食|た}べる`. Из одной записи content-build получает фуригану для показа (`<ruby>`) и кана-вариант для допустимых ответов. В рантайме не нужен морфологический анализатор, всё детерминировано и проверяется при сборке.

**Типичные ошибки — заблуждения, а не опечатки:** `つ / っ` (сокуон), `や / ゃ`, `か / が` (дакутэн), долгие гласные `おう / おお`, частицы `は / が`, `に / で`. Они пишутся шаблонами ошибок, как в английском.

**Родной язык.** Узбекский тоже агглютинативный, с порядком SOV и послелогами (`-ni` ≈ `を`, `-da` ≈ `で / に`). Блок контраста с узбекским для японского особенно ценен и пишется отдельно от русского, как и в английском.

**Интерфейс и шрифт.** Geologica не покрывает CJK: для японского текста — Noto Sans JP с сабсеттингом по используемым символам на этапе сборки. Фуригана включается и выключается учеником; с N3 по умолчанию только над новыми кандзи.

**Не делаем в первой версии:** рукописный ввод и порядок черт, оценку тона (pitch accent) — она придёт вместе со speaking (docs/05).

## Математика

Математика — реальная цель: для автора и для учеников в Узбекистане, где таких продуктов почти нет. Её ядро проверки — модуль в refl-core, детерминированный, no\_std + alloc, одинаковый в content-build и в WASM.

### Программа: своя, из лучшего

Цель — эталонный курс математики, который сильнее лучших продуктов индустрии (например, Brilliant) по точности диагноза и адаптивности, при этом без ИИ в рантайме. Поэтому граф тем не копирует ни одну программу целиком. Связи «что нужно знать до чего» строятся по логике самой математики и по исследованным траекториям обучения. Из каждого источника берётся то, в чём он сильнее остальных.

| Источник | Берём | Не берём |
| --- | --- | --- |
| траектории обучения (Clements, Sarama) | уровни мышления в раннем счёте, мере и геометрии → мелкий граф классов 1–4 | — |
| сингапурская математика | конкретное → наглядное → абстрактное; модель отрезков для текстовых задач; меньше тем в год, но глубже | учебниковую подачу |
| японская школа (structured problem solving) | одна задача — несколько решений и их сравнение: задания «реши другим способом», «какое решение лучше и почему» | — |
| Эльконин — Давыдов | величины и отношения до чисел, дроби через измерение, ранняя алгебраическая запись → граф дробей и начал алгебры | — |
| китайское обучение вариацией (bianshi) | серии, где меняется один параметр (docs/12) | — |
| Cognitive Tutor, Carnegie Learning | мелкие KC, проверка по шагам, ошибочные правила | — |
| ALEKS, теория пространств знаний | граф уточняется по данным, а не только экспертно | закрытую модель |
| Brilliant | интерактивные исследования: меняешь параметр — видишь, что меняется | ИИ-тутор, серии дней, лиги |
| кружковая традиция и задачники для сильных | обогащающий трек задач на рассуждение и доказательство | — |
| государственный стандарт Узбекистана | только карта соответствия «класс → темы», чтобы ученик видел, что поддерживает школьную программу | порядок тем и метод |

**Принципы программы:**

1. **Виды KC различаются:** понятие, процедура, числовой факт (нужна беглость), стратегия решения задач, перевод между представлениями. У каждого вида своя лестница заданий и свой критерий освоения: факту нужен автоматизм, понятию — несколько представлений, стратегии — перенос на незнакомые задачи.
2. **Задача до объяснения** (docs/12, шаг 1), и объяснение отвечает на трудность, с которой ученик только что столкнулся.
3. **Перевод между представлениями — отдельный навык:** «по рисунку составь выражение», «по выражению нарисуй полосу», «по графику найди уравнение».
4. **Заблуждения с первого дня:** у каждой KC процедуры — каталог ошибочных правил (docs/10, «Ошибочные правила»), собранный из исследований типичных ошибок.
5. **Задачи в контексте и чистые задачи различаются:** разрыв между ними — отдельное состояние ученика (docs/03, «Расширенная диагностика»).
6. **Граф проверяется данными:** скрытые пререквизиты видны в аудите контента (docs/11, К2) и исправляются в графе.

**Рецензент.** Корректность задач проверяет ядро, но педагогику — порядок, представления, каталог ошибок — должен вычитывать практикующий учитель математики. Без этого «эталонность» остаётся заявлением.

**Как понять, что получилось лучше.** Прямо сравнить с чужим продуктом нельзя: его логов у нас нет. Сравниваемся с собой и с внешними якорями по метрикам docs/11: точность прогноза, удержание освоенного через 30 дней, время до освоения, результаты на внешних задачах известного уровня.

### Числа и выражения

- **Точная арифметика:** рациональные числа на целых произвольной длины (`num-bigint` / `num-rational` без std). Десятичный ответ переводится в рациональное точно: `0,75` = `3/4`. Float в проверке не участвует.
- **Выражения:** AST на индексном пуле (`Vec<Node>` + `NodeId`), разбор из текстовой записи, вывод в каноническую форму.
- **Эквивалентность v1:** многочлены и рациональные функции от нескольких переменных с рациональными коэффициентами. Для этого класса нормальная форма (раскрытые скобки, приведённые подобные, сокращённая дробь, упорядоченные одночлены) даёт **точный** ответ «эквивалентно / нет» — без проверки в случайных точках.
- **v2:** радикалы вида a√b, табличные значения тригонометрии, логарифмы. Там, где нормальной формы нет, — проверка в контрольных точках с фиксированным seed, исключая точки вне области определения; это записывается в версию проверщика.
- **Область определения.** Задание указывает, должна ли преобразованная запись сохранять область определения: `x²/x` и `x` эквивалентны только при `x ≠ 0`.

**Проверка самого движка.** Ошибка в канонизации тихо портит вердикты всем ученикам, поэтому движок проверяется строже остального ядра:

- **property-тесты:** каноническая форма совпадает со значением исходного выражения в сотнях случайных рациональных точек (в тестах, не в рантайме); две эквивалентные формы дают одну каноническую;
- **метаморфные тесты:** перестановка слагаемых и множителей, раскрытие скобок, переименование переменных, умножение на 1 не меняют вердикт;
- **ошибочные правила:** для каждого правила тест подтверждает, что оно меняет значение, и что найденный контрпример действительно опровергает его;
- **золотой корпус:** пары «эквивалентно / нет» и ловушки области определения от рецензента-учителя; корпус растёт из нераспознанных ответов учеников;
- **детерминизм:** одинаковые входы дают побайтово одинаковые канонические формы в native и WASM.

Внешний CAS как эталон в CI не используется: это второй язык и вторая реализация, а три уровня тестов выше дают ту же уверенность без них.

### Правильный ответ = эквивалентность + форма

Эквивалентности мало. В задании «раскройте скобки (x+1)²» ответ `(x+1)²` эквивалентен эталону, но неверен. У слота есть **требование к форме** — предикат над AST: раскрыто, разложено на множители, несократимая дробь, смешанное число, стандартный вид, без иррациональности в знаменателе и т. п. Вердикт:

| Эквивалентно | Форма | Вердикт |
| --- | --- | --- |
| да | да | верно |
| да | нет | ошибка, заблуждение «не доведено до требуемой формы» своего навыка |
| нет | — | сравнение с ошибочными правилами, иначе не распознано |

**Синтаксис ввода.** Ответ печатается текстом (`2x^2 + 3/4`, `sqrt(2)`) или собирается математической клавиатурой интерфейса. Разбор идёт в WASM на лету и показывает ответ в нормальной записи до отправки. Нераспознаваемая запись не отправляется и событием не становится: это не ответ, а незаконченный ввод.

### Ошибочные правила

У заблуждения математики может быть **исполняемое правило** — перепись над AST: `(a+b)² → a² + b²`, `a/b + c/d → (a+c)/(b+d)`, `−(a − b) → −a − b`. Оно даёт три вещи:

1. **Ожидаемые ошибки без ручного авторства:** проверщик применяет правила заблуждений, привязанных к KC слота, к эталонному решению; совпавший результат — диагноз.
2. **Дистракторы** для заданий с выбором — тем же путём.
3. **Контрпример:** перебором малых целых (детерминированный порядок) находятся значения, на которых левая и правая части правила различаются: «при a = 1, b = 2: (1+2)² = 9, а 1² + 2² = 5». Это микро-объяснение заблуждения (docs/12, «Опровержение»).

content-build проверяет, что правило заблуждения действительно меняет значение (иначе это не ошибка) и что эталон не совпадает ни с одним ошибочным результатом.

### Генераторы задач

Шаблон задачи — запись контента: параметры с диапазонами и ограничениями, выражение задачи, вид ответа, требование к форме, KC и заблуждения слотов. Ядро по `(item_id, version, seed)` детерминированно строит экземпляр: параметры, эталонный ответ, пошаговое решение (если задание многошаговое), ожидаемые ошибки по правилам заблуждений.

- **ГПСЧ** — свой, описанный в спеке и версионированный (SplitMix64), чтобы экземпляр совпадал в native и WASM и не зависел от версии чужого crate.
- **seed** выбирает планировщик детерминированно и записывает в событие (`ItemRef.seed`).
- **Проверка при сборке:** content-build строит первые 256 экземпляров каждого шаблона и проверяет ограничения: ответ существует и «красивый» по правилам шаблона, ошибочные правила дают результаты, отличные от эталона и друг от друга, дистракторы различимы. Один провал — ошибка сборки со seed-свидетелем.
- **Калибровка** сложности идёт на семью (шаблон = семья), как уже устроено в docs/03; экземпляры делят её.

С генераторами контент математики дешевле английского: один проверенный шаблон даёт неограниченное число заданий.

### Многошаговые решения

Шаг решения — слот. У многошагового задания слоты открываются по порядку, у слота может быть `depends_on` — шаги, от результата которых он зависит.

- **После ошибки на шаге** ученик видит верный результат этого шага и решает следующий от него. Следующий шаг проверяется обычным образом; ошибка не «тянется» дальше и не наказывает соседние KC. Перенос ошибки с засчитыванием последствий (error carried forward) — возможное улучшение позже, не v1.
- **Затухание разбора** (docs/12): уровень scaffold s — сколько первых шагов показано уже решёнными. Показанные шаги не дают событий; решаемые — обычные ответы со своими KC. Уровень пишется в событие.
- **Арифметический промах** внутри алгебры виден, только если вычисление — отдельный шаг со своей KC арифметики. Тогда штраф получает эта KC, а не цель задания — тот же принцип, что «опечатка не наказывает грамматику».

### Визуальные примитивы

Для младших классов наглядность обязательна (CPA, docs/12). Набор компонентов клиента: числовая ось, полосы и площади для дробей, координатная плоскость и графики, геометрический холст, графы, матрицы и векторы. Контракт: стимул содержит декларативное описание примитива (данные из бандла), а интерактивный ответ — структурированный `Response` (точка, значение на оси, выбранные элементы). Учебная логика в TypeScript не пишется: проверка — в ядре.

### Дальний горизонт: не проектируем

**Конструктор доказательств** для вузовского уровня (пошаговая сборка вывода из правил с проверкой каждого шага) по сути требует своего proof assistant. Записан в планы, но не проектируется, пока не закрыты школьные треки.

## События и схема

Изменения схемы событий вносятся сейчас, пока `schema_version = 1` и нет учеников (docs/02, «Событие и лог»):

| Изменение | Зачем |
| --- | --- |
| `ItemRef.seed: Option<u64>` | экземпляр генератора |
| `AnswerEvent.scaffold: u8` | уровень затухания разбора, 0 — без разбора |
| `AnswerEvent.revealed_deps: bool` | шаг решался от показанного верного результата предыдущего |
| `Response`: новые варианты вместе с видами заданий (`order`, `pairs`, `expr`, `point`) | структурированные ответы; правило для неизвестных вариантов у старых клиентов — в очереди этапа 0 |

События контроля качества — в docs/11.

## Порядок работы

1. **Этап 0 (сейчас):** `ItemKind` как трейт + `ItemBody`; предмет и шкала в контенте; префикс предмета в слагах; изменения схемы событий. Английский переходит на новую границу без изменения поведения.
2. **Этапы 1–2:** только английский. Граница проверяется тем, что английский живёт на ней целиком.
3. **Трек «Математика»** после этапа 2: модуль выражений и генераторы, классы 1–6 (арифметика, дроби, начала алгебры), визуальные примитивы; затем 7–9 и 10–11.
4. **Трек «Японский»** — когда найден вычитывающий носитель.

## Открытые вопросы

1. **Программа математики.** Решено: своя, из лучших источников (раздел «Программа: своя, из лучшего»); стандарт Узбекистана — только карта соответствия классов. Открыто: кто вычитывает педагогику.
2. **Язык задач по математике.** Стимул на языке интерфейса (uz / ru / en): у математики, в отличие от английского, сам текст задания переводится.
3. **Вузовские треки:** какие (матанализ, линейная алгебра, дискретная математика) и в каком порядке.
4. **Вычитка японского:** кто и на каких условиях.
